# Pre-push gate

`.githooks/pre-push` is the tracked hook a push runs. `lu_machinery/install_git_hooks.sh` installs a delegator that execs the copy in the current worktree. A consumer checkout runs the installer from the installed release, with its working directory in that checkout. Its `--check` reads the declared stages with the release's own interpreter selector and stage reader, resolved through the hook boundary (`project_hook_context_resolve`): `LEARN_UKRAINIAN_PRIMARY_REPO_ROOT` must be set, and the interpreter is `LEARN_UKRAINIAN_PYTHON` when set, else that primary's `.venv/bin/python`. The agent git shim (`lu_machinery/agent_runtime/shims/git`) pins `core.hooksPath` to `lu_machinery/opsec/push_hooks` for `git push`, so Git runs that directory's `pre-push`. That hook execs `lu_machinery.opsec.git_push`. After a clean scan, `lu_machinery/opsec/push_hooks/chain` runs the caller's own pre-push hook with the same arguments and input.

## What the hook runs

The hook saves Git's ref updates, then:

1. When Git passes the remote name and URL, the hook requires a readable `lu_machinery/opsec/git_push.py`. A missing file prints `OPSEC: push scanner unavailable; push refused.` and exits 1. Otherwise it runs `.githooks/pre_push_gate.py --push-messages`. That entry checks every destination ref under `refs/heads/entire/` or `refs/tags/entire/`, including deletions. It allows those updates only when the publication scanner would exempt the same push as private: `prepublish.is_private` names the destination's `fleet_repos.yaml` row, the URL is a plain `https://` (optional port 443), `ssh://`, `git+ssh://` or `ssh+git://` (optional port 22) or scp-like GitHub `owner/name` URL (`PRIVATE_ENTIRE_URL`: no other port, query, fragment, password or other userinfo characters), and `git_push.trusted_route` verifies the transport, with the Git `git_push.main` uses. A repository whose `public-` row names the destination by its `github` or `alternate_github` slug, an unknown destination, an unverified route, or an unreadable registry causes a refusal. The entry then calls `git_push.main` unless Git already ran the scanner from its `push_hooks` directory. The metadata lookup uses a separate `git_push.Repository` with `pin_hooks=False` to read the push's inherited hook configuration. Ordinary scanner reads retain the default `core.hooksPath=/dev/null` pin.
2. `check_owned_paths push` (`lu_machinery/dispatcher/ownership.py`) when `LEARN_UKRAINIAN_DISPATCH_TASK_ID` is set and that module is present. A dispatched write task whose pushed branch commits touch a path outside its owned paths exits 1. A read-only task, a task with no owned paths, or a check that cannot run exits 0. Settlement still checks the delivery.
3. `.githooks/check-pytest-stamp.py`. It does not run pytest. An update of `refs/heads/main` whose diff touches `tests/`, `lu_machinery/`, `scripts/`, `curriculum/` or `agents_extensions/shared/rules/` needs a pytest stamp for the local branch whose age is at most 600 seconds (`MARKER_MAX_AGE_SECONDS` in `.githooks/pytest_stamp.py`). `SKIP_PYTEST_HOOK=1` skips the check. A missing, mismatched or older stamp exits 1.
4. When Git passed the remote name and URL, `git-lfs` must be on `PATH` (exit 2 when it is not) and `git lfs pre-push` runs on the same updates.

With no arguments the hook skips the scanner and Git LFS, and still runs the owned-path check and the stamp check. No push path runs pytest. A green push is not evidence that the suite passed.

The scanner reads remote ref names, annotated tag names and messages (nested tags included) and the raw messages of commits reachable from the sent ids, including mergetag text. It does not read file contents. A deletion publishes no text. Commits reachable from the verified head of the destination's registered public default branch are left out of the scan. A destination is left unscanned only when the catalogue marks it private and Git reaches it on the trusted transport route; every other destination is scanned as public. A malformed update, a graft, a shallow boundary inside the scanned range, `GIT_SHALLOW_FILE` in the environment, a scanner error or the deadline refuses the push (exit 1). The deadline is 300 seconds. `LU_OPSEC_PUSH_SCAN_TIMEOUT` replaces it and must be a positive finite number; any other value refuses the push. `LU_OPSEC_REAL_GIT`, when it is an absolute executable path, is the git binary the scan and `chain` use. `LU_OPSEC_OVERRIDE`, set for that command only, is offered to the private override authority after a finding. `chain` unsets it before the caller's hook. A finding prints `OPSEC blocked:` with the rule, class, field and line, and does not print the matched text.

## What a push does not run

The hook does not run `pre-commit`, `lint_opsec_leaks.py --commit-range` or `check-no-internal-ids`. This repository has no `.pre-commit-config.yaml`. The hook uses `--push-messages` as its Python entry point. The legacy `main()` entry holds admission, stage and run budgets, the concurrent scope, receipts and measurements. Its product stage always raises `validation_incomplete`. That entry reads `LU_PRE_PUSH_GATE_ADMISSION_WAIT_S`, `LU_PRE_PUSH_GATE_STAGE_BUDGET_S`, `LU_PRE_PUSH_GATE_RUN_BUDGET_S`, `LU_PRE_PUSH_GATE_MAX_CONCURRENT_RUNS` and `LU_PRE_PUSH_GATE_RUN_TOKEN`. None of those variables apply to a push.

## Untracked inputs and deployed agent outputs

`main()` refuses a push (`untracked_inputs`) when an untracked or ignored `*.py`, `*.pth`, `pytest.ini`, `tox.ini`, `setup.cfg` or `pyproject.toml` lies outside the outgoing commit (`reject_untracked_inputs`). Two derived sets are exempt. The first is dependency files under a `node_modules` directory whose sibling `package-lock.json` is tracked. The second is the current output of the installed agent deploy (machinery#22).

The installed deploy (`python -I -m lu_machinery.agent_deploy --project-root <checkout>`) writes release-owned and product-owned files into the provider directories `.agent`, `.agents`, `.claude`, `.codex` and `.cursor`, with its ownership manifest at `.deploy-state/agent-deploy.v1.json`. Agent sessions run their hooks from those copies, so a worker must not delete them to push. When a listed file lies in a provider directory, the gate runs the deploy's own check in the interpreter that runs the gate: `python -I -m lu_machinery.agent_deploy --project-root <checkout> --check --print-manifest --inputs-commit <outgoing head>`. With `--inputs-commit` the check reads the descriptor and the product sources from the outgoing commit's Git objects, never from the checkout. It walks the commit's tree objects by ID with `git cat-file --batch` and checks that every object it reads hashes to the ID it asked for. Git resolves no path, so `core.worktree` and other path settings cannot redirect a lookup, and replace refs are ignored. The plan therefore depends only on the commit ID, and nothing written to the checkout, its refs, its configuration or its object store while the check runs can change it. The gate's own listings of the checkout (`status`, `ls-files`) pass `--work-tree=<checkout>` with the untracked cache and file-system monitor off, so neither `core.worktree` nor cached or monitor state from the checkout's configuration can change what they list. The plan comes from those sources and the installed release. The check verifies every planned output and the checkout's manifest against it, writes nothing, and prints the plan's manifest. The gate never reads the checkout's manifest file. A file is exempt only if all of these hold:

- the check exits 0;
- the file is a regular file, not a symlink;
- its SHA-256 and mode equal its record in the manifest the check printed.

The digest of the printed manifest joins the receipt (`agent_deploy`). Everything else stays refused, and the refusal states why: an edited or stale copy, an extra file, a symlink, a copy deployed from uncommitted sources, or a check that fails or cannot run. To fix it, commit the agent extension sources, run the deploy again, then push. Known gap: `git ls-files --others` does not descend into a symlinked directory or an untracked nested repository, so files under one are never listed and never refused. `.githooks/pre-push` in this repository does not call `main()`. A consumer whose pre-push hook does call it gets this behaviour.

## Bypass

`git push --no-verify` tells Git to skip hooks. The agent git shim refuses that option, and any argument whose name is at least three characters and a prefix of `--no-verify`, before Git runs (`OPSEC: --no-verify would skip the push scan; push refused.`, exit 2). It also refuses a push when `GIT_CONFIG` is set, when `--shallow-file` is passed, or when the scanner hooks, `git_push.py` or the project interpreter cannot be used. Those refusals exit 2.

## Merge-main rule

Merge `origin/main` into a worker branch only when `git merge-tree` against a freshly fetched main SHA reports a conflict, when the driver disposes on base/head/combined-tree evidence that the branch is incompatible with the base, or on driver order. A merge-tree error is unknown, not a conflict. Every new head needs renewed approval and CI; merge-group CI stays the authority for semantic combinations.
